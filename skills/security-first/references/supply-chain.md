# Dependency scans, static analysis and release artifacts

For a product that ships something people install or download. The scans protect them
from known vulnerabilities; the artifacts let them check that what they got is what you
built. Each rule below cost a rebuild or a false alarm in a real release.

## Known-vulnerability scans

- **Scan inside the release build, before the installer exists.** The vulnerability
  database changes every day. A scan run after packaging found two vulnerable components
  (an embedded web server and a bundled database library), which forced a rebuild and a
  new published checksum. Fail the build at a set severity (for example CVSS 7).
- **Read each CVE before acting.** Scanners match by product name (CPE): a
  development-only tool inherited the CVE of an editor plugin with a similar name, and a
  database driver inherited one of that database's command-line shell. Read the
  description and the affected version range in the report.
- **Fix real ones by upgrading.** Prefer the framework's patch release that brings the
  fixed transitive dependency over pinning the transitive by hand.
- **Suppress false ones narrowly**: by package URL plus CVE id, each with a written
  reason, in a file under version control. Never by product name alone, and never by
  turning the scanner off.
- **The scanner's API key is a machine setting.** Check which environment the build
  actually reads (user or system variables); a key set in the wrong one makes the scan
  slow or skipped.

## Static analysis

- **Security linters raise false alarms by name and by shape.** A preference field
  called "key" was read as a hard-coded password, and every record holding a list was
  flagged as exposing its internals even though it stored an immutable copy. Justify each
  exclusion, with its reason, in a versioned file; never switch a detector off.
- **A regular-expression denial-of-service warning is fixed by bounding** the
  quantifiers and the input length. If the detector still fires, justify it in the same
  file.

## Release artifacts

- **An SBOM is generated by the build** and shipped next to the installer.
- **The checksum next to a download comes from that exact file**, computed by the build or
  the release script, never typed by hand.
- **Never rebuild an artifact that was already shared** to test the release script. A
  packager that is not reproducible gives a new hash, and the checksum already published
  becomes false. Test the script against the artifact that exists, compare its output
  with the known value, and add a control run that must fail (a file that is not the
  installer).

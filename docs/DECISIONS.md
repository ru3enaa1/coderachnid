# Decisions

Short records of the choices that shape coderachnid. Newest last.

## D-001 · A plugin, not a single skill (2026-10-13)

A single skill would load everything at once or nothing at all. A plugin bundles several
focused skills that activate independently, and installs from GitHub in two commands.

## D-002 · Three layers: senses, guards, templates (2026-10-13)

Instructions alone are suggestions an agent can skip. Skills (*senses*) are paired with
*guards* (tests, scripts and architecture rules that verify) and *templates* (the same
project shape every time). Guards ship after the skills have been tested; see the roadmap
in `CLAUDE.md`.

## D-003 · English for all plugin content (2026-10-13)

The target audience is international. Skills, references, templates and docs are written
in English. Projects that use the plugin can still respond in their own language.

## D-004 · No hooks by default (2026-10-13)

Nothing runs on every turn unless the user opts in. Any hook shipped later is optional,
documented and off by default.

## D-005 · Original content only (2026-10-13)

No text copied from other plugins or skill packs, whatever their license. Ideas may be
cited; text is written here.

## D-006 · Every rule comes from a real failure, generalized (2026-10-13)

The rules were distilled from the maintainer's previous projects and stripped of names,
paths, customers and private details. Each rule keeps its reason and points to a check.

## D-007 · Name: coderachnid (2026-10-13)

The spider feels every thread of its web and senses the faintest vibration before
anything breaks: a sixth sense added to a model that is already intelligent, making it
sharper and more precise.

## D-008 · Visual identity and voice (2026-10-13)

The README opens with a character, a one-line tagline, honest badges and a banner,
followed by a short second-person welcome. The character is a hand-drawn spider sticker
with an amber `< >` on its back; amber is the only accent color and marks "the sense"
in every piece (the bracket in the logo, the vibrating thread in the banner). Voice:
short, dry sentences that state what the plugin does. It names the $20 monthly plan,
whose usage limits reset every few hours, as the main audience without excluding any
other.

No unmeasured numbers, rankings, star counts or third-party trophies appear anywhere.
Every figure on the front page is a fact the repository can prove, and
`guards/check-skills.sh` fails if the skill count shown drifts from the folders.

The artwork is SVG generated by `assets/build-assets.mjs` with fixed seeds, so it is
reproducible and reviewable as text. Text inside the SVGs uses system monospace fonts,
because an SVG shown through `<img>` on GitHub cannot load web fonts.

## D-009 · Always-on behavior lives in the rules file, not in skill activation (2026-10-13)

Skills are chosen per task from their descriptions. In F2, `response-closing` loaded on
only some development replies whatever its wording, so a rule meant for every reply
cannot rely on it. Behavior that must happen on every turn goes in the project rules
file (`CLAUDE.md`), which `project-setup` writes from `CLAUDE.template.md`; the skill
keeps the details that line points to. Evidence: `docs/F2-EVALUATION.md`.

## D-010 · Every guard has a positive control; project guards ship as templates (2026-10-13)

A guard is trusted only after it has failed on a known-bad fixture, so every rule of
every guard has one in `guards/tests/test-guards.sh`. The suite caught a real bug on its
first run (a line-ending check that could never see CRLF on Windows). Guards meant for
other projects live in `skills/project-setup/templates/guards/`, so the skill that sets
up a project can copy them and `check-skills.sh` verifies the paths it mentions exist.

## D-011 · The closing ships as an opt-in output style (2026-10-14)

D-009 put always-on behavior in the rules file, which meant one line in every project.
A plugin can ship output styles, and `keep-coding-instructions: true` keeps Claude Code's
default instructions while the style adds only its own. `coderachnid:closing` adds the
five-point block and nothing else. Users select it once, per project or in
`~/.claude/settings.json`; it is not forced (`force-for-plugin` stays off), so it never
overrides a style the user chose. The `CLAUDE.md` line remains for those who prefer it.
Evidence: three headless runs with the style selected. An English task and a Spanish task
ended with the block (labels translated), and a one-line question did not get it.

## D-012 · Field lessons: one new skill, the rest in existing ones (2026-10-15)

An analysis of a full project lifecycle (about 1,300 tool calls) found that the value
was in disciplines applied in the main thread, not in orchestration, and listed
practices worth generalizing. Each became original text with its reason and check.
Only `sourced-data` became a new skill: it has a trigger no other skill covers. The
data-as-code practices went into a `precise-code` reference instead of a skill of their
own, because every skill's description costs tokens in every session and competes in a
listing whose budget is 1% of the context window; a reference loads only when needed.

## D-013 · Hooks ship as a second, opt-in plugin in the same repository (2026-10-24)

Long conversations re-read their whole context on every message, and resuming one after
the prompt cache expires re-sends all of it. Claude Code lets hooks see the transcript,
inject a file into a new session and react to compaction, but no hook can clear a
session. So the design keeps one manual step (`/clear`) and automates the rest: a
`handoff` skill writes `.coderachnid/HANDOFF.md`, and hooks ask for it past a token
threshold and reload it in the next session. D-004 holds: the hooks live in
`coderachnid-relay`, a second plugin listed by the same marketplace and installed only by
those who want it. The handoff lives in `.coderachnid/`, not `.claude/`, because Claude
Code asks permission for every write under `.claude/` (found in a real session).
`market-research` sets `disable-model-invocation`, so it costs nothing until it is run.

## D-014 · Discovery runs as a chain of by-hand skills, one file each (2026-10-24)

`market-research` answered "is it worth building?" but left a gap before code: what to
sell, at which price, and what the first version looks like. Two skills close it,
`offer` and `product-brief`, and `market-research` gains the inputs they need (the top
ten problems ranked by urgency × willingness to pay, and the free position among the five
main competitors). All three set `disable-model-invocation`, so they cost nothing in
sessions that don't run them, and each writes one file the next one reads
(`docs/MARKET.md` → `docs/OFFER.md` → `docs/BRIEF.md`), so each can run in its own
session with the handoff carrying the thread. The design direction lives in a reference
loaded only by `product-brief` (Art-Directed Editorial), written in original words from
patterns seen in modern landing pages, with no brand names and no reused art; the user's
own identity always overrides it, and polishing is left to a design tool. Both new skills
are marked anticipated (D-006) until used on a real project.

Update (2026-10-24): at the maintainer's request the anticipated mark was replaced by the
measured result of the chain evals (`docs/F2-EVALUATION.md`), with the note that neither
skill has met a real project yet. A fictional fixture proves the skills deliver what
they promise; only a real project can show what they miss.
